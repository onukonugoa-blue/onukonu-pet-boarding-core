This is a fresh Replit session.

The objective is to implement the first production version of OPSMAIL.

OPSMAIL is an Operational Intelligence Layer.

It is NOT a customer notification system.

It is NOT a replacement for SMTP.

It is NOT a workflow engine.

It is NOT a task management system.

It is NOT a Telegram integration.

OPSMAIL is a curated operational event queue designed for future consumption by:

- Telegram Bots
- Operations Groups
- AI Summarizers
- Task Generators
- Reporting Systems

---

CRITICAL NON-NEGOTIABLE REQUIREMENT

ZERO REGRESSION.

Existing functionality must remain completely untouched.

The following systems must continue functioning exactly as they do today:

✓ OTP emails

✓ Client Portal access

✓ Customer notifications

✓ Booking confirmation emails

✓ Invoice emails

✓ Contact form emails

✓ SMTP configuration

✓ Existing notification channels

✓ Existing mail templates

✓ Existing workflows

OPSMAIL must be additive only.

No existing email path may be intercepted, modified, wrapped, rerouted, delayed or replaced.

If there is uncertainty:

Preserve current behaviour.

---

OPSMAIL DESIGN PRINCIPLE

OPSMAIL is NOT an audit log.

OPSMAIL is NOT a generic event bus.

OPSMAIL is a queue of operationally significant events.

Only events that may require:

- Awareness
- Coordination
- Assignment
- Escalation
- Follow-up
- Review

should enter OPSMAIL.

The intended future flow is:

OPB
↓
OPSMAIL Queue
↓
OPSMAIL Mailbox
↓
Telegram Group
↓
Manager Action

The business database remains the source of truth.
