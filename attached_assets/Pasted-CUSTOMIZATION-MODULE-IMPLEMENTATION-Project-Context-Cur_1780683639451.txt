CUSTOMIZATION MODULE IMPLEMENTATION

Project Context

Current baseline:

Git commit:
"Update to production version 1.7.3 with bug fixes and cleaned debug logs"

This build is considered stable.

The goal of this task is to introduce a centralized Customization subsystem.

This is a new feature.

Do not redesign any existing operational workflows.

Do not alter booking, client, pet, kennel, inquiry, onboarding, invoice, or payment logic.

The purpose is to move business-owned content out of code and into configurable settings.

---

## OBJECTIVE

Create:

Settings
└── Customization

This becomes the authoritative source for:

* Terms & Conditions
* Legal text
* WhatsApp templates
* Email templates
* Onboarding instructions
* Facility information
* Public operational messaging

Future wording changes must not require code changes or deployment.

---

## NAVIGATION

Add:

Settings
└── Customization

Access:

* Admin = View + Edit
* Manager = View Only

---

## STORAGE

Create new table:

opb_customizations

Fields:

id
setting_key (unique)
setting_value (longtext)
category
updated_at
updated_by

Use a flat key/value model.

Do not create separate tables for every content type.

## SECTION 1 — TERMS & CONDITIONS

Create editable rich-text fields:

* Boarding Terms & Conditions
* Additional Policies
* Privacy Notice
* Operational Notes

Onboarding pages must render these values dynamically.

No hardcoded legal text should remain in source files.

---

## SECTION 2 — ONBOARDING COMMUNICATIONS

Create editable templates:

* Onboarding Email Subject
* Onboarding Email Body
* Onboarding WhatsApp Message
* Resend Onboarding Message
* Onboarding Completion Message
* Onboarding Step Instructions

Supported placeholders:

{{CLIENT_NAME}}
{{FACILITY_NAME}}
{{ONBOARDING_LINK}}
{{PHONE}}
{{EMAIL}}

---

## SECTION 3 — INQUIRY COMMUNICATIONS

Create editable templates:

* Inquiry Acknowledgement Subject
* Inquiry Acknowledgement Message
* Inquiry Follow-Up Message
* Inquiry Acceptance Message
* Inquiry Rejection Message

---

## SECTION 4 — FACILITY INFORMATION

Editable values:

* Facility Name
* Support Phone
* Support Email
* Website
* Business Hours

These values must be reusable inside templates.

Facility Name should override the default WordPress site name when OPB-generated communications are rendered.

---

## SECTION 5 — TEMPLATE ENGINE

Create one shared rendering engine.

All placeholders must be resolved through the same renderer.

Preview rendering and production rendering must use the same code path.

Do not create separate renderers.

---

## SECTION 6 — TEMPLATE PREVIEW

Create a Preview tab.

Allow administrators to:

* Select a template
* Preview rendered output
* View placeholder substitutions

Use sample values.

Examples:

CLIENT_NAME = Demo Customer

FACILITY_NAME = Demo Facility

ONBOARDING_LINK = https://example.com/onboard/abc123

---

## SECTION 7 — TEMPLATE VALIDATION

Validate placeholders.

Examples:

Valid:

{{CLIENT_NAME}}

Invalid:

{{CLIENTNAME}}

Display warnings for unsupported placeholders.

Prevent accidental template mistakes.

---

## SECTION 8 — TERMS VERSIONING

Track:

* Version Number
* Updated At
* Updated By

When onboarding acceptance occurs in future workflows:

The accepted version should be available for recording.

Do not redesign onboarding.

Simply ensure version metadata exists and is maintained.

---

## SECTION 9 — EXPORT

Add:

Customization
→ Export Configuration

Export all settings as JSON.

Include:

* setting_key
* setting_value
* category
* updated_at
* updated_by

Purpose:

* Backup
* Recovery
* Migration
